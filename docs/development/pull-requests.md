# Pull Request 规则

PR 的目标是让另一位维护者能够判断：问题是否值得解决、方案是否符合产品方向、风险是否受控、证据是否足够。代码量不是质量证明。

## 提交前

以下改动先创建 Issue 并达成方向共识：

- 改变默认阅读体验、产品非目标或自动行为；
- 新增权限、远程服务、持久数据、模型调用或费用路径；
- 修改存储 schema、连接器协议、扩展身份或发布格式；
- 大型 UI 重构、跨三个以上运行时边界的功能；
- 引入运行时依赖或超过 200 KB 的分发资源。

明确 Bug、小型可访问性修复、测试、文档和不改变行为的局部重构可以直接提交 PR。

## 范围

- 一个 PR 解决一个可说明的问题。
- 不把无关重构、格式化、依赖升级和功能实现混在一起。
- 采用完整切换：迁移所有调用者，删除被替代路径，不长期保留未承诺的兼容别名。
- 超过约 800 行人工编写 diff 时，优先按可独立验证的边界拆分；生成文件、模型和锁文件不计入。

行数只是提醒，不是硬性拒绝标准。若无法拆分，在 PR 描述中说明依赖关系和审查顺序。

## 标题与提交

PR 标题使用：

```text
<type>: <简短结果>
```

允许的 `type`：`feat`、`fix`、`docs`、`refactor`、`test`、`chore`、`release`。

示例：`fix: stop passive analysis in on-demand mode`

提交历史应能帮助审查。默认使用 squash merge；只有提交本身代表需要保留的独立迁移或可回退阶段时才保留多提交历史。

## PR 描述必须包含

1. **问题**：当前可观察到什么错误或缺口；
2. **方案**：采用什么边界，为什么不选明显替代方案；
3. **产品影响**：是否改变默认体验或产品方向；
4. **数据与权限**：发送、保存、清理、无痕窗口、权限和费用是否变化；
5. **验证**：自动检查、真实浏览器场景和必要截图；
6. **文档**：更新了哪些用户说明、设计系统、隐私文档、ADR 或开发记录。

不适用的项目写“无变化”或“不适用”，不要删除检查项。

## 必须通过的检查

所有 PR：

```bash
npm ci
npm run check
```

另外按类型提供证据：

| 改动 | 额外证据 |
| --- | --- |
| Bug 修复 | 修复前可复现、修复后不再出现；适合时保留回归测试 |
| Popup / 设置页 | 实际扩展页面截图；键盘和 axe 检查 |
| 注入网页 UI | 至少一个浅色和一个深色真实页面；关闭后无残留 |
| 权限 / 数据 | 数据流说明、无痕行为、清理路径和隐私文档 |
| 模型 / 路由 | 成功、格式错误、限流、认证失败和回落路径 |
| 存储迁移 | 旧数据升级、失败安全模式、清理与未来版本拒绝 |
| Connector | 安装、重连、协议不匹配、退出和错误脱敏 |
| Release | `npm run release:package`、校验和及解压产物检查 |

手动场景从 [`docs/verification-checklist.md`](../verification-checklist.md) 选择，不要求每个 PR 重跑全部清单。

## 审查门槛

`.github/CODEOWNERS` 将全部路径归属 `@rockythink`。其他维护者可以审查、请求修改和批准，但这些批准不能替代仓库所有者的最终批准。由其他人提交的 PR 必须获得 `@rockythink` 的 Code Owner approval 才能合并。

仓库所有者提交自己的 PR 时无法批准自己的改动，因此保留管理员绕过能力；只有在自动检查通过、阻塞讨论解决且下列要求满足后才使用该能力。所有者可以拒绝或延后任何与产品方向、隐私边界或维护成本不一致的改动。

PR 可合并需要：

- 自动检查通过；
- 非所有者提交的 PR 已获得 `@rockythink` 最终批准；
- 所有阻塞讨论已解决；
- 用户可见、隐私、架构和开发记录文档已同步；
- 不包含密钥、令牌、私人正文、URL、诊断日志或本机路径；
- PR 分支没有未解决冲突。

维护者可以要求拆分范围、补充真实浏览器证据，或拒绝与产品方向冲突的功能，即使代码本身可运行。

## 合并后

- 使用 squash merge 时，最终提交标题沿用 PR 标题；
- 破坏性变更、迁移或重要修复应关联开发记录；
- 需要发布时另开 Release PR，不在普通功能 PR 中顺带改版本号；
- 合并后发现回归，优先回退可疑改动，再在独立 PR 中修复。
